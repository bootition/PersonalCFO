# 备份与恢复（加密归档）

> 目标：`journals/raw/reports/close/config/paisa.db` 这些 **gitignore 的敏感数据**也能防误删、防磁盘故障；
> 主仓库与账本仓（journals/.git）只覆盖 journals 的一部分，**不能替代本方案**。

## 1. 备份策略（三层）

| 层 | 内容 | 频率 | 位置 |
|---|---|---|---|
| L1 本地 git | 主仓（代码/文档/配置模板）+ 账本仓（journals） | 每次改动（SOP 步骤 5） | 本机 |
| L2 加密归档 | **全部敏感数据**：journals、raw 账单、reports、close、config、paisa.db、敏感信息文件 | 每月 SOP 后 + 任何破坏性操作前（如 `reset_init.py`） | `backups/*.pcfobak` |
| L3 异地 | 把最新的 `.pcfobak` 复制到网盘/U盘（文件已加密，可安全外放） | 同 L2 | 用户自行 |

- 归档格式：AES-256-GCM，key = PBKDF2-HMAC-SHA256(密码, salt, 600k)；密码文件 `config/backup_secret.txt`（首次运行自动生成，gitignore，**绝不进归档**）。
- 保留策略：默认保留最近 10 份，自动清理更旧的。
- RPO≈1 个月（或每次重要操作前）；RTO≈5 分钟（见第 4 节恢复流程）。

## 2. 生成备份

```bash
cd <仓库根>
venv/Scripts/python scripts/backup.py backup
# 输出示例：文件 325 个 / 原始 22.2 MB → 归档 5.9 MB + sha256
```

- 首次运行会生成 `config/backup_secret.txt` 并提示：**立刻把密码抄进密码管理器**；密码丢失 = 归档永久无法恢复。
- 也可用 `--password` 或环境变量 `PCFO_BACKUP_PASS`（CI/脚本场景）。
- 默认保留最近 10 份；清理旧归档前会打印"将删除 N 份"（如需保留更多用 `--keep N`）。
- 查看本地归档：`venv/Scripts/python scripts/backup.py list`

## 3. 校验（恢复演练，建议每月做一次）

```bash
venv/Scripts/python scripts/backup.py verify backups/personalcfo-<ts>.pcfobak
```

它会：解密 → 解压到临时目录 → 对照清单逐文件校验 sha256 → 用还原出的 journals 跑
`hledger check balanced` → 打印结论并自动清理临时目录。
全部 ✅ 才算"备份可用"，任何一项 ❌ 都要重新生成备份。

## 4. 恢复

```bash
# 先校验
venv/Scripts/python scripts/backup.py verify backups/personalcfo-<ts>.pcfobak
# 恢复到临时目录（不直接覆盖现账本）
venv/Scripts/python scripts/backup.py restore backups/personalcfo-<ts>.pcfobak --to .planning/restore-<ts>
# 人工比对无误后，再替换：
#   - 整仓恢复：把还原目录内容拷回仓库根（先手工备份当前 journals/raw/...）
#   - 只恢复账本：拷 journals/*.journal 回去，然后
venv/Scripts/python src/finance.py check
venv/Scripts/python scripts/reconcile-check.py
vendor/paisa/paisa.exe update --config paisa_test/paisa.yaml    # 重新灌库
```

注意：
- `restore` 不会自动覆盖现有文件；目标目录非空需 `--force`。
- 恢复后 DB 建议用 `paisa update` 重建（`paisa_test/paisa.db` 也可直接从归档还原，但重建更干净）。
- Git Bash 下若提示信息乱码，先 `export PYTHONIOENCODING=utf-8`（或直接在 cmd 里跑）。

## 5. 接入月度 SOP

在 `01_月度SOP.md` 步骤 5（账本仓提交）之后加一步：

```bash
venv/Scripts/python scripts/backup.py backup
venv/Scripts/python scripts/backup.py verify backups/personalcfo-<最新>.pcfobak
```

破坏性操作前（重置初始化、批量改账本、升级 Paisa fork）**必须先做一次 backup**。

## 7. 代码 / Paisa fork 备份（P7.18，2026-09-12 红队复核后修订）

Paisa fork 是独立 git 仓，**不在主仓库历史里**，单独备份：

| 资产 | 位置 | 内容 |
|---|---|---|
| 私有仓（历史） | `https://github.com/bootition/PersonalCFO-paisa`（private，分支 `master`） | **32 提交可克隆历史**（`05e9d06`：1 个上游基座提交 + 31 个 fork 提交，含 P7.19），浅边界重建产物 |
| **可恢复历史 bundle** | 同仓 Release `fork-2026-09-12-valid` 资产 + 本地 `backups/paisa-fork-valid-*.bundle` | 与私有仓 master 同源；`git bundle verify` + `git clone` 双向验收通过（6.17 MB） |
| 上游参照 | `git -C vendor/paisa remote -v` → `upstream` = ananthakumaran/paisa | 升级/diff 用 |

恢复：

```bash
# 直连私有仓（已含 32 提交历史）
git clone https://github.com/bootition/PersonalCFO-paisa.git paisa-restore
# 或用 release 里的 bundle 资产 / 本地 backups/*.bundle
git clone backups/paisa-fork-valid-<ts>.bundle paisa-from-bundle
```

### 7.1 为什么不能直接对 vendor/paisa 跑 `git bundle --all`

`vendor/paisa/.git` 是**浅克隆**（`.git/shallow`），且 gc 后存在缺失对象。
- 直接 `git push` → 远端 `index-pack failed`；
- 直接 `git bundle create --all` → 要么 `Failed to traverse parents of commit 0c8301e…`，要么生成**看似 verify 通过但 `git clone` 报 missing object 的坏 bundle**（2026-09-12 红队实测）。
- **发布前必须做 clone 验收**：`git clone <bundle> /tmp/x && git -C /tmp/x rev-list --count HEAD`。

### 7.2 正确做法：把浅边界变成新根，重建 31 个提交

```bash
BOUND=0c8301e950ce0a7b6bf9896fbe2bb6eb734f31de   # .git/shallow 里的边界提交
ts=$(date +%Y%m%d-%H%M%S)
rm -rf .planning/fork-rebuild .planning/fork-patches && mkdir -p .planning/fork-rebuild .planning/fork-patches
git -C vendor/paisa archive $BOUND | tar -x -C .planning/fork-rebuild
( cd .planning/fork-rebuild && git init -q -b master && git add -A \
  && git commit -q -m "upstream paisa base（浅克隆边界树快照）" )
git -C vendor/paisa format-patch --binary --full-index -o "$PWD/.planning/fork-patches" $BOUND..HEAD
( cd .planning/fork-rebuild && for p in ../fork-patches/*.patch; do git am -q --3way "$p"; done )
# 校验：提交数 = 32，HEAD tree 与原仓一致
git -C .planning/fork-rebuild rev-list --count HEAD
git -C .planning/fork-rebuild rev-parse HEAD^{tree}   # 应等于 git -C vendor/paisa rev-parse HEAD^{tree}
# 生成 bundle + clone 验收 + 上传 release
git -C .planning/fork-rebuild bundle create "$PWD/backups/paisa-fork-valid-$ts.bundle" --all
rm -rf /tmp/verify && git clone backups/paisa-fork-valid-$ts.bundle /tmp/verify && git -C /tmp/verify log --oneline | wc -l
gh release create "fork-$ts-valid" "backups/paisa-fork-valid-$ts.bundle" \
  --repo bootition/PersonalCFO-paisa --title "Paisa fork 可恢复 bundle（$ts）" \
  --notes "浅边界重建：1 基座 + 31 fork 提交；bundle verify + clone 双验收"
# 私有仓 history 分支（网络允许时）：
git -C .planning/fork-rebuild remote add origin https://github.com/bootition/PersonalCFO-paisa.git
git -C .planning/fork-rebuild -c 'http.https://github.com.proxy=' -c http.proxy= push -f origin master
```

> 经验：本机到 github.com 的 **git-over-HTTPS 经常超时/被重置**，但 `gh`（API）可用，
> 所以 release 资产上传比 `git push` 可靠；大包推送失败时不要反复重试，直接走 bundle+release。

fork 里每次构建产物（`web/static`）不入 git，避免仓库再次膨胀。
