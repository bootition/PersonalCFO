# 个人财务系统升级 · GitHub 选型研究报告

- 日期：2026-09-06
- 研究目录：`D:\Mr.Q\掌控经济\新建文件夹`（所有 clone/下载/实验都在此目录）
- 输入：现有工具需求提炼（已由用户授权自行决定保留/舍弃）+ 复式记账升级访谈 25 条决策

## 1. 结论（推荐方案）

**方案 A：hledger 复式记账引擎 + double-entry-generator 账单导入器 + full-fledged-hledger 工作流 + 自研薄壳（Python 编排 + Edge PDF）**

- 会计引擎、五张报表、结账/反结账、季度累计口径、CSV/HTML 导出：全部用现成的 hledger（已实测）。
- 支付宝/微信/多家银行/券商账单 → 复式账本：用 double-entry-generator（deg，已实测全链路）。
- 文件组织、增量重建报表、把原始账单当唯一事实源：抄 full-fledged-hledger 与 hledger-flow 的模式。
- 自研部分只剩：规则配置、期初建账模板、结账快照脚本、财报汇总 HTML→PDF、月度对账清单 —— 都是"胶水"，不是会计引擎。
- 已在 `prototype/` 做出可运行原型，并生成 2026 年 Q1/H1/Q3/年报的 txt/html/csv/PDF。

**为什么不是其他方案**：见第 4 节对比表。

## 2. 保留 / 舍弃决策（现有 finance-catch）

用户已确认"现有工具没有值得迁移的东西"，由我决定。我的决定是：

| 现有能力 | 决策 | 新体系中的落点 |
|---|---|---|
| 支付宝/微信账单导入 | 保留（行为） | deg 解析，输出 hledger journal |
| 分类规则（观察→自动） | 保留（行为） | deg 的 YAML 规则文件；"改规则→重新生成账本"天然可回滚 |
| 待确认队列 | 保留（行为） | `Assets:FIXME` / `Expenses:FIXME` 科目余额即待办清单 |
| 退款必须关联原消费 | 保留（行为） | deg 内置退款反向匹配；hledger 冲销分录 |
| 批次撤销 | 保留（行为） | 原始账单保留，重跑导入覆盖生成文件 = 撤销/重做 |
| 审计轨迹 | 保留（行为） | 账本是纯文本，git 提交历史即审计 |
| 概览统计/环比/排行 | 由四期财报取代 | hledger 报表 |
| 单式 ledger_entries/SQLite schema | 舍弃 | 不迁移代码与表结构 |
| FastAPI/HTMX 页面 | 舍弃（暂） | 先用 CLI+hledger-web；需要时再包 Web 壳 |
| 历史 1966 条账本数据 | 不逐笔迁移 | 从原始账单（账单位置见本地敏感文件，不入库）重新导入；升级日盘点录入期初 |
| 73 条分类规则 | 语义迁移 | 转写为 deg 规则（config/alipay.yaml、wechat.yaml 已给出初版） |

## 5. 下一步建议（按此顺序推进）

1. 把 `raw/` 指向真实账单目录（或复制到 raw/），用 `config/*.yaml` 跑 `finance.py import`，检查 FIXME 账户余额清单，迭代规则直到 FIXME 收敛到可接受范围。
2. 盘点各账户真实余额，在 journals 里录入"期初余额"分录（模板见 prototype/config/科目表草案.md）。
3. 把历史 2025-08~2026-07 账单重导入生成历史账本；用 `report 2025` / `report 2026` 生成对照财报。
4. 补 hledger 定期规则（工资计提、折旧、房租摊销），报表命令加 `--forecast`。
5. 需要时把 finance.py 包成 FastAPI 页面或直接用 hledger-web；PDF 用现有 Edge headless 链路。
6. 可选：从 Beancount-Trans 抄支付宝/微信解析与映射模板（MIT），补 deg 的组合支付拆分短板。
